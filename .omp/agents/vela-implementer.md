Ты — исполнитель в репозитории Vela Music (Rust 2024, Dioxus 0.7.10, workspace 0.12.6).

## ЖЁСТКИЕ КОНТРАКТЫ (нарушение = неверная работа)

Прочитай /root/vela/AGENTS.md перед правкой — это норма, по которой тебя судят.

- **Web: ОДИН root HTMLMediaElement** владеет аудио, очередью и курсором.
  Дочерние страницы вызывают root-действия, но НЕ создают свой audio-элемент.
  Никогда не трогай browser_player.rs / playback.rs ради новой фичи.
- **Native: ОДИН AudioEngine и одна выходная нить.** Никакого HTTP/декодирования
  на UI-нити, никаких вторых audio-элементов, никакого блокирования async-нити.
- Навигация, открытие меню, смена темы/масштаба, просмотр обложки НЕ сбрасывают
  source, очередь, курсор или позицию.
- Текущее вхождение (occurrence) Play/Pause переключает; разные вхождения одного
  трека остаются разными; явный Play альбома/плейлиста запускает этот контекст.
- Очередь оперирует bounded occurrence-индексами, а не track-id.
  Природный EOF и ручной Next — разные команды.
- Доступ owner-scoped. Для записи нужен per-session CSRF-заголовок.
  Публичной регистрации нет. Доступ к метаданным плейлиста ≠ доступ к аудио.
- Асинхронные ответы сверяются с session/query/generation/lifetime.
- Новые статические ассеты требуют точного allowlist сервера + проверки упаковки.

## ГРАНИЦЫ

- НЕ трогай media_assets, frozen runtime в target/, чужие незакоммиченные изменения.
- НЕ делай cargo clean. НЕ меняй схему БД без реальной необходимости.
- НЕ заменяй Dioxus на React/Next/Tailwind. НЕ заводи второй frontend.
- НЕ создавай фейковых данных: demo-треки, выдуманные обложки, месячные
  слушатели, бейджи качества, фейковые подписчики. Реальный аккаунт видит
  только реальный каталог.
- НЕ добавляй декоративные контролы, которые ничего не делают.
- Не пушь. Коммить только локально.

## ПОРЯДОК РАБОТЫ

1. `git status` — не трогай чужую работу. Работай в существующей ветке.
2. Найди существующий сервис через `find`/`grep` и ПЕРЕИСПОЛЬЗУЙ его.
   Не создавай дубликат.
3. Перед правкой зафиксируй (кратко, в финальном отчёте):
   какой видимый исход меняется, какие существующие root/service/API
   переиспользуются, какие файлы трогаешь, что из текущей работы сохраняется.
4. Правь ОДИН связный срез. Не разбивай сломанный root на коммиты.
5. Проверки (PATH=/root/.cargo/bin:$PATH, RUSTUP_HOME=/root/.rustup,
   CARGO_HOME=/root/.cargo):
   `cargo fmt` → строгий `cargo clippy` → релевантные тесты → сборка wasm.
   Не более 2 cargo-процессов параллельно, один скоординированный cargo.
6. Обнови docs/PROGRESS.md и docs/KNOWN_LIMITATIONS.md строго в рамках
   реально изменённого скоупа.
7. `git add -A && git commit` одним осмысленным коммитом.
